# Teledash Processing Backend

_ML-powered processing services for Telegram data analysis_

## About

The Teledash Processing Backend extends the main Teledash application with machine learning capabilities. It provides:

- **Semantic search**: Find messages by meaning using vector embeddings for text and images
- **Audio transcription**: Automatic speech recognition (ASR) using Whisper models
- **Text classification**: Detect conspiracy narratives and other content categories
- **Customizable models**: Configure different models and parameters for your use case

This is an **optional** component of Teledash. The main backend works without it, but you'll miss out on ML-powered features.

## Repositories

- [Frontend](https://github.com/ARAI-Telegram/teledash-frontend) - Web interface
- [Backend](https://github.com/ARAI-Telegram/teledash-frontend) - Core API and worker services for data collection and management
- **Processing Backend** (this repository)(optional) - ML-powered services (semantic search, transcription, classification)

## Requirements

- **Teledash Backend**: Must be running (provides Elasticsearch, object storage, and calls semantic search APIs)
- **S3-compatible Object Storage**: Same as main backend (AWS S3, MinIO, Hetzner, Cloudflare R2, etc.)
- **[Docker](https://docs.docker.com/get-docker/)**: Required. GPU support (NVIDIA Container Toolkit) strongly recommended for ASR, optional for other services

## Configuration

### How Configuration Works

Teledash Processing uses the same three-tier configuration system as the main backend:

1. **`common/settings.py`** - Contains default values for all Python application settings. **Do not edit this file.**
2. **`.env.example`** - Template showing all available configuration options.
3. **`.env`** - Your local configuration file. Values here override defaults in `settings.py`. The file is not part of the repository, instead can be created by copying the template `.env.example`, see below.

### Setup Instructions

1. Copy `.env.example` to `.env`:
   ```bash
   cp .env.example .env
   ```

2. **Required**: Fill in the following values (must match your main backend configuration):
   - `STORAGE_ACCESS_KEY` - Your storage provider access key
   - `STORAGE_SECRET_KEY` - Your storage provider secret key
   - `STORAGE_BUCKET_PREFIX` - Must match main backend exactly (leave empty if main backend has no prefix)

3. **Docker Compose Variables**: These are already set in `.env.example` with defaults. Modify if needed:
   - `COMPOSE_PROJECT_NAME` - Keep default or customize
   - `TELEDASH_DOCKER_NETWORK` - Must match main backend's `COMPOSE_PROJECT_NAME` + `_default` **only if both backends run on the same machine**. Remove or comment out if on different machines.
   - `ELASTIC_HOST`, `ELASTIC_PORT` - Must match main backend's Elasticsearch configuration
   - `REDIS_PORT` - Keep default (6379) or change if conflicts with main backend Redis
   - `GPU_USE`, `GPU_DEVICE` - Configure GPU usage (see GPU Configuration section)
   - Service-specific ports: `TEXT_FAST_API_PORT`, `IMAGE_FAST_API_PORT`

4. **Python Settings (Optional)**: Uncomment any settings in the bottom section of `.env` to override their defaults in `settings.py`

## GPU Configuration

**GPU vs CPU performance:**
- **Classification, Text & Image Search**: Run well on CPU (even on modern laptops)
- **ASR (Transcription)**: GPU strongly recommended for acceptable performance


**To enable GPU support:**

1. **Install NVIDIA Container Toolkit** on your host system:
   ```bash
   # Ubuntu/Debian
   distribution=$(. /etc/os-release;echo $ID$VERSION_ID)
   curl -s -L https://nvidia.github.io/nvidia-docker/gpgkey | sudo apt-key add -
   curl -s -L https://nvidia.github.io/nvidia-docker/$distribution/nvidia-docker.list | sudo tee /etc/apt/sources.list.d/nvidia-docker.list
   sudo apt-get update && sudo apt-get install -y nvidia-container-toolkit
   sudo systemctl restart docker
   ```

2. **Configure `.env`**:
   ```env
   GPU_USE=true
   GPU_DEVICE=0  # or 1, 2, etc. if multiple GPUs
   ```

3. **Uncomment GPU sections in `docker-compose.yml`**:
   - Look for `# Uncomment for GPU support` comments
   - Uncomment the `deploy.resources.reservations.devices` sections for `classification-worker` and `asr-worker` services

4. **Verify GPU is available** after starting containers:
   ```bash
   docker exec -it classification-worker nvidia-smi
   ```

**For CPU-only mode**: Keep `GPU_USE=false` in `.env` (default). GPU sections in `docker-compose.yml` can stay commented out.

## Deployment

### Network Setup

The Processing Backend needs to communicate with:
- **Elasticsearch** (from main backend - to read/write messages and embeddings)
- **Object Storage** (same as main backend - to download media files)
- **Main Backend** (required - the semantic search APIs are called by the main backend)

#### Same Machine Deployment (Recommended)

**Important**: This deployment mode requires both backends to run on the **same physical/virtual machine**.

If both backends run on the same machine:

1. **Ensure Docker network name matches**: The `TELEDASH_DOCKER_NETWORK` variable in processing backend's `.env` must equal the main backend's `COMPOSE_PROJECT_NAME` + `_default` suffix
   
   Example:
   ```env
   # Main backend .env
   COMPOSE_PROJECT_NAME=teledash
   
   # Processing backend .env
   TELEDASH_DOCKER_NETWORK=teledash_default
   ```

2. **Default settings work automatically**: Container names like `elastic:9200` and `minio:9000` resolve via Docker network

#### Different Machine Deployment

**Important**: If backends run on different machines, Docker networks cannot be shared.

If the Processing Backend runs on a **different machine** than the main backend:

1. **Update `.env`** with actual IP addresses/hostnames:
   ```env
   ELASTIC_HOST=<main-backend-server-ip>  # e.g., 192.168.1.100
   STORAGE_ENDPOINT=<storage-server-ip>:9000  # e.g., 192.168.1.100:9000
   # Remove or comment out TELEDASH_DOCKER_NETWORK
   ```

2. **Update `docker-compose.yml`**:
   - Remove or comment out the `networks` section that references `${TELEDASH_DOCKER_NETWORK}`
   - Ensure ports are exposed for external access

3. **Configure firewalls** to allow communication between machines

### Starting Services

**Start all services:**
```bash
docker compose --profile all up --build -d
```

**Start specific services:**
```bash
# Only ASR transcription
docker compose --profile asr up --build -d

# Only text classification
docker compose --profile classification up --build -d

# Both text and image semantic search
docker compose --profile text-search --profile image-search up --build -d

# Multiple services
docker compose --profile asr --profile classification up --build -d
```

**Using environment variable:**
```bash
COMPOSE_PROFILES=classification,asr docker compose up --build -d
```

### Available Profiles

- `all` - All services
- `asr` - Audio transcription worker
- `classification` - Text classification worker
- `text-search` - Text embedding worker + API
- `image-search` - Image embedding worker + API

## Development

### Prerequisites

We use [VS Code Remote-Containers](https://code.visualstudio.com/docs/devcontainers/containers) for development. This setup provides isolated development environments with all dependencies pre-configured.

**Development vs Production Storage:**
- **Production** (`docker-compose.yml`): Uses named Docker volumes for models and temp files (persistent, managed by Docker, survives container restarts)
- **Development** (`docker-compose.debug.yml`): Uses local bind mounts to `tmp/` directories (easier to inspect, modify, and clean up during development)

### Setup

**1. Create temporary directories for models and data:**

```bash
mkdir -p services/asr/tmp
mkdir -p services/classification/tmp
mkdir -p services/semantic_text_search/api/tmp
mkdir -p services/semantic_text_search/embedding_worker/tmp
mkdir -p services/semantic_image_search/api/tmp
mkdir -p services/semantic_image_search/embedding_worker/tmp
chmod 755 services/*/tmp services/semantic_*/*/tmp
```

**Note**: Models are downloaded to `tmp/model/` subdirectories within each service. The specific subdirectory name depends on the model being used.

**2. Open a service in a dev container:**

Run the **Remote-Containers: Open Folder in Container** command from VS Code Command Palette and select one of:
- `services/asr`
- `services/classification`
- `services/semantic_text_search/embedding_worker`
- `services/semantic_text_search/api`
- `services/semantic_image_search/embedding_worker`
- `services/semantic_image_search/api`

**3. Run services:**

Use the **Run and Debug** panel (`Shift+Cmd+D` on macOS) and click **Start**.

### Triggering Tasks Manually

Each worker service has a trigger script for testing:

```bash
# Classification (with optional flag to clear previous results)
python trigger_classification_task.py
python trigger_classification_task.py --clear

# ASR transcription
python trigger_asr.py
python trigger_asr.py --clear

# Text embeddings
python trigger_embedding_task.py
python trigger_embedding_task.py --clear

# Image embeddings
python trigger_image_embedding.py
python trigger_image_embedding.py --clear
```

**⚠️ Warning**: The `--clear` flag deletes all previous results for that task from the database. Use with caution!

### Starting Celery Beat Schedulers

To enable automatic periodic task execution in development:

```bash
# Example for classification
celery --app=worker.main beat --loglevel=DEBUG

# Or with INFO level
celery --app=worker.main beat --loglevel=INFO
```

### Rebuilding After Configuration Changes

**Important**: If you modify `.env`, always rebuild without cache:

```bash
docker compose --profile all build --no-cache
docker compose --profile all up -d
```

A normal rebuild (`--build`) is **not sufficient** because environment variables are baked into the image at build time.

### Running Tests

To run the test suite inside a container:

```bash
python3 -m pytest common/tests/ -v
```

## How It Works

The Processing Backend operates as a set of independent workers that:

1. **Query Elasticsearch** for unprocessed messages at configured intervals
2. **Download media files** from object storage when needed (ASR, image search)
3. **Process data** using ML models:
   - **ASR**: Transcribes audio/video using faster-whisper (optimized Whisper implementation)
   - **Classification**: Detects conspiracy narratives using TelConGBERT (fine-tuned BERT model)
   - **Text embeddings**: Generates semantic vectors for messages using sentence-transformers
   - **Image embeddings**: Generates semantic vectors for images using CLIP models
4. **Store results** back to Elasticsearch:
   - Transcriptions added to message documents
   - Classifications stored in separate classification result indices
   - Embeddings stored in vector indices for kNN search

**Semantic Search APIs** provide FastAPI endpoints that:
- Accept text/image queries from the main backend
- Generate embeddings for queries using the same models
- Perform kNN vector search in Elasticsearch
- Return ranked results by semantic similarity

All processing happens locally with no external API dependencies.

## Monitoring and Resource Management

### Docker Resource Limits

Adjust CPU and memory limits in `docker-compose.yml` under each service's `deploy.resources.limits` section based on your hardware and model sizes.

Default limits work for medium-sized models. Larger models (e.g., `large-v3` for ASR, large CLIP variants) may require more resources.

### Monitoring Tools

**Container logs** provide detailed information:
```bash
# Follow logs for specific service
docker compose logs -f classification-worker

# View logs from all services
docker compose logs -f
```

**Kibana** (optional): Available for Elasticsearch data exploration and visualization. It's commented out in both `docker-compose.yml` and `docker-compose.debug.yml` by default. To enable:

1. Uncomment the `kibana` service section in your docker-compose file
2. Start with: `docker compose up kibana -d`
3. Access at: http://localhost:5601

For production monitoring, consider tools like Prometheus + Grafana or ELK stack.

## Troubleshooting

**Models not downloading:**
- Check `LOAD_MODELS_FROM_HUGGINGFACE=true` in `.env`
- Verify internet connectivity from containers
- Check disk space in `tmp/model/` directories

**GPU not detected:**
- Verify NVIDIA Container Toolkit installation: `docker run --rm --gpus all nvidia/cuda:11.8.0-base-ubuntu22.04 nvidia-smi`
- Check `GPU_USE=true` in `.env`
- Ensure GPU sections are uncommented in `docker-compose.yml`
- Verify GPU device index with `nvidia-smi` on host

**Cannot connect to Elasticsearch:**
- Verify `ELASTIC_HOST` and `ELASTIC_PORT` match main backend
- **For same machine**: Ensure `TELEDASH_DOCKER_NETWORK` is correct and both backends are running
- **For different machines**: Use IP address instead of container name, and remove `TELEDASH_DOCKER_NETWORK` from `.env`
- Check Elasticsearch is running: `curl http://<ELASTIC_HOST>:<ELASTIC_PORT>`

**Port conflicts:**
- Change `REDIS_PORT`, `TEXT_FAST_API_PORT`, or `IMAGE_FAST_API_PORT` if conflicts occur
- Check what's using ports: `lsof -i :<port_number>` (macOS/Linux)

**Out of memory errors:**
- Reduce batch sizes: `*_MODEL_BATCH_SIZE` and `*_FETCH_BATCH_SIZE` settings
- Use smaller models (e.g., `small` instead of `medium` for ASR)
- Reduce concurrent workers (e.g., `ASR_CONCURRENCY=1`)
- Increase Docker memory limits in `docker-compose.yml` (for CPU mode)
- For GPU memory errors: Use smaller models or reduce batch sizes

**Processing too slow:**
- Switch from CPU to GPU mode for 10-100x speedup (requires NVIDIA Container Toolkit)
- Set `GPU_USE=true` in `.env`, uncomment GPU sections in `docker-compose.yml`, rebuild containers
